# Monte Carlo Simulation — Оркестрируемый пайплайн анализа строительных проектов

*Прототип системы вероятностного моделирования*

## Описание

Агентно-ориентированный пайплайн вероятностного моделирования строительных проектов — от парсинга графика КСГ до генерации аналитических заключений. Система объединяет детерминированную и стохастическую модели через мультиагентную архитектуру: детерминированный блок строит WBS-иерархию и выявляет логические зависимости между этапами с помощью LLM-кандидат-агентов (multi-round consensus), топологический анализ выполняется алгоритмом Флойда–Уоршалла; вероятностный блок обрабатывает карту рисков, формирует семантический граф взаимозависимостей и вычисляет весовые коэффициенты (структурное затухание + семантическая оценка), формируя байесовскую сеть для вероятностного вывода. Результат — 200 000 итераций симуляции Монте-Карло с расчётом квантилей P50/P80/P90/P95, оценкой доверительных интервалов методом bootstrap (1 000 ресемплингов при размере выборки 200 000, 95% уровень надёжности), stacked торнадо-анализом вклада каждого риска в задержку и бюджет, анализом чувствительности через корреляции Пирсона, 2D тепловой картой плотности совместных сценариев (задержка vs бюджет) с контурами уровня и radar-чартами ключевых корреляций, а также итоговым заключением, сгенерированным LLM. Для моделирования совместного хвостового риска (корреляция между срывом сроков и перерасходом бюджета) применяется Link-Copula (ρ ≈ 0.5).

**Справочно:** при отключении LLM (`use_llm=False`) пайплайн вычисляется как базовый сценарий без учёта взаимозависимостей между рисками (независимые риски, единичные маргинальные вклады).

**Ключевые принципы:**
Пайплайн построен на консенсус-схеме: N независимых LLM-кандидат-агентов параллельно выполняют запросы, результаты голосуются (мода/среднее) без промежуточных агентов (строитель/критик удалены). Каждый этап координируется оркестратором из `main.py`. Такая архитектура обеспечивает модульность, возможность параллельного выполнения и переиспользования кэша.

## Логика работы пайплайна

Проект состоит из 10 последовательных шагов:

| # | Что делает | Простыми словами |
|---|------------|------------------|
| **1** | Парсит КСГ (Excel/CSV) → строит иерархию задач | Берём график работ, извлекаем задачи с кодами WBS |
| **2** | LLM-агенты ищут логические связи между этапами | Нейросеть читает названия задач и определяет зависимости: «после заливки фундамента можно начинать монтаж каркаса» |
| **3** | Парсит карту рисков (CSV/XLSX) | Извлекает текстовые описания и числовые оценки рисков |
| **4** | LLM-агент привязывает риски к этапам | Определяет: «риск срыва поставки бетона относится к этапу СМР» |
| **5** | Строит граф зависимостей рисков | Определяет, какие риски влияют на какие, и на каком расстоянии по графу |
| **6** | Рассчитывает веса связей (структурные + семантические) | Оценивает силу влияния рисков: «задержка бетона → перерасход бюджета» со шкалой 0–1 |
| **7** | Строит Байесовскую сеть | Создаёт вероятностную модель: при наступлении одного риска, как меняется вероятность других |
| **8** | Запускает Monte Carlo симуляцию | 200 000 раз «проигрывает» сценарии и смотрит, какие сроки и бюджеты наиболее вероятны |
| **9** | Визуализирует результаты | Строит графики, торнадо-анализ, тепловые карты |
| **10** | LLM-агент формирует аналитическое заключение | Нейросеть пишет итоговый отчёт с рекомендациями |

## LLM-консенсус в проекте

Мультиагентная схема консенсуса: N независимых **кандидат-агентов** параллельно выполняют LLM-запросы (консенсус-режим), после чего результаты голосуются напрямую, без промежуточных агентов (строитель/критик):
- **шаги 2 и 4** — агрегация по **моде** (частота голосов): для рёбер/привязки рисков выбираются модальные значения;
- **шаг 6** — усреднение семантических весов по раундам.

Результат кэшируется целиком — повторный запуск пропускает все LLM-запросы.

**Схема консенсуса:**

```
┌─────────────────────────────────────────────────────────┐
│  Оркестратор (main.py)                                  │
│                                                         │
│  ┌──────────────────────────────────────────────────┐   │
│  │  Кандидат-агенты (consensus-раунды)              │   │
│  │  Agent-1: «связь между СМР и отделкой?»          │   │
│  │  Agent-2: «связь между фундаментом и каркасом?»  │   │
│  │  ... (N раундов, параллельно)                    │   │
│  └────────────────────────┬─────────────────────────┘   │
│                           │                             │
│  ┌────────────────────────▼─────────────────────────┐   │
│  │  Очистка (cleaning)                              │   │
│  │  Фильтрация кандидатов, лимиты, ацикличность     │   │
│  └────────────────────────┬─────────────────────────┘   │
│                           │                             │
│  ┌────────────────────────▼─────────────────────────┐   │
│  │  Агрегация (мода — шаги 2/4, среднее — шаг 6)    │   │
│  │  Итоговые рёбра / привязки / веса                │   │
│  └──────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────┘
```

**Как работает консенсус:**

1. **Кандидат-агенты** — N независимых LLM-запросов (раундов) параллельно ищут логические связи между парами WBS-этапов (шаг 2) или привязывают риски к вершинам (шаг 4). Каждый раунд аргументирует свои предложения.

2. **Мода (шаги 2, 4)** — результаты всех раундов голосуются: для каждого риска/пары выбираются модальные значения (связь/вершина, набравшие наибольшее число голосов).

3. **Среднее (шаг 6)** — семантические веса усредняются по всем раундам, результат кэшируется.

### Шаг 6: Модельные допущения

Этот шаг рассчитывает весовые коэффициенты рёбер семантического графа рисков. Каждому ребру присваиваются три величины:

1. **Структурный вес** — затухает с топологическим расстоянием между рисками в графе (чем дальше вершины, тем слабее структурное влияние). Формула линейного затухания:
   ```
   structural(d) = a + (b − a) × (1 − d / D)
   ```
   где `d` — расстояние по графу (алгоритм Флойда–Уоршалла), `D` — диаметр графа, `a` и `b` — параметры затухания. Риска на одной вершине (`d = 0`) получает вес `w0 = 1.0`.

2. **Семантический вес** — смысловая близость пары рисков, оценённая LLM-агентом по шкале 0–1 (consensus-режим, N раундов).

3. **Финальный вес** — комбинация структурного и семантического компонентов:
   ```
   final = min(1.0, semantic × (1 + structural(d)))
   ```

**Параметры:**

| Параметр | Описание |
|----------|----------|
| `structural_decay.mode` | Режим расчёта: `continuous` (по умолчанию) |
| `structural_decay.a` | Вес связи на максимальном расстоянии (d = D), по умолчанию `0.0` |
| `structural_decay.b` | Вес связи на минимальном расстоянии (d = 1), по умолчанию `0.7` |
| `structural_decay.w0` | Вес для рисков на одной вершине, по умолчанию `1.0` |
| `structural_decay.diameter` | Диаметр графа (0 = вычислить автоматически из шага 5) |
| `threshold` | Минимальный финальный вес для включения связи |
| `llm.temperature` | Температура LLM при семантическом взвешивании |

При D=7, a=0.0, b=0.7:
| Расстояние | Вес |
|------------|-----|
| 0 | 1.0 (w0) |
| 1 | 0.600 |
| 5 | 0.200 |
| 7 | 0.000 |

### Шаг 7: Байесовская сеть

Байесовская сеть (BN) — направленный ациклический граф (DAG), где узлы — бинарные случайные величины `Ri ∈ {0, 1}` (0 — риск не реализуется, 1 — реализуется), рёбра — причинно-следственные связи из семантического графа рисков.

На каждом ребре `(Rj → Ri)` назначен **финальный вес** `Wij` — единый коэффициент, объединённый на шаге 6 из структурного затухания и семантической оценки:
```
Wij = min(1.0, semanticij × (1 + structural(dij)))
```

**Таблица условных вероятностей (CPT):** для каждого узла `Ri` с родителями `Parents(Ri)` базовая вероятность `Pbase(Ri = 1)` (из `probability_min/max` реестра) корректируется мультипликативными факторами:

```
P(Ri = 1 | Parents(Ri)) = Pbase(Ri = 1) × ∏ adjustmentj,
```
где
```
  adjustmentj = 1 + Wij,   если Rj = 1 (родитель реализовался)
  adjustmentj = 1.0,        если Rj = 0 (родитель не реализовался)
```

Таким образом, каждый реализовавшийся родитель усиливает вероятность потомка пропорционально весу связи `Wij`, полученному из Шаг 6. CPT покрывает все комбинации состояний родителей (2^{|Parents(Ri)} строк).

**Пример:** если у узла `Ri` два родителя `R1` и `R2` с финальными весами `W1 = 0.4` и `W2 = 0.3`, и реализовался только `R1`, то:
```
P(Ri = 1 | R1=1, R2=0) = Pbase × (1 + 0.4) × 1.0 = Pbase × 1.4
```

### Шаг 8: Monte Carlo

Каждая итерация симуляции работает как стохастический «прогон» проекта: Байесовская сеть определяет, какие из N рисков реализуются (бинарная генерация по CPT с учётом причинных связей), для каждого наступившего риска случайным образом извлекается дельта задержки (Δдни) из треугольного/нормального распределения и дельта бюджета (Δруб) из реестра, задержки суммируются в `total_delay`, прямые бюджетные влияния — в `budget_risk_impact`; затем копула-механизм конвертирует задержку в косвенный бюджет (`Δdelay × cost_per_day × ρ`), распределяя его пропорционально вкладу каждого риска, и итоговый `total_budget_impact` = прямые + косвенные расходы. Повторяя 200 000 раз, получаем эмпирическое распределение сроков и бюджетов, из которого извлекаются квантили P50/P80/P90/P95, доверительные интервалы (Bootstrap) и распределение сценариев для последующей визуализации.

| Параметр | Описание |
|----------|----------|
| Итерации | Число прогонов симуляции (по умолчанию `200_000`, из `monte_carlo.iterations`) |
| `random_seed` | Seed для воспроизводимости (по умолчанию `42`) |
| `distribution.type` | Тип распределения дельт рисков: `normal` (нормальная аппроксимация треугольного распределения, по умолчанию) или `triangular` |
| `normal_sigma_div` | Делитель для sigma: `sigma = (max−min) / N`, по умолчанию `6` (±3σ ≈ 99.7% охвата треугольного распределения) |
| `complete_date` | Целевая дата завершения проекта (из `project.complete_date`) |
| `base_budget` | Базовый бюджет (из `project.base_budget`) |

**Формулы:**
- `Delay = Σ (Ri × ImpactDelayᵢ)` — суммарная задержка как взвешенная сумма дельт
- `Budget = Σ (Ri × ImpactBudgetᵢ)` — суммарный перерасход как взвешенная сумма дельт
- `P50, P80, P90, P95` — квантили эмпирического распределения результатов симуляции
- **Распределение дельт рисков:** реальные дельты рисков имеют треугольное распределение с параметрами `(min, mode, max)`. Для ускорения вычислений используется нормальная аппроксимация этого распределения: `σ = (max − min) / 6`, что обеспечивает охват ±3σ ≈ 99.7% площади треугольного распределения. При `distribution.type = triangular` используется оригинальное треугольное распределение без аппроксимации.
- **Копула (Link-Copula)** — для учёта зависимости между срывом сроков и ростом бюджета применяется параметрическая копула: корреляция между маргинальными распределениями задержек и бюджетных дельт моделируется через коэффициент `ρ` (по умолчанию `0.5`). Это позволяет учитывать совместный хвостовой риск — одновременное наступление крупных срывов по срокам и перерасходу — без предположения о многомерной нормальности, что более адекватно для не-гауссовых дистрибуций дельт рисков.
- **Алгоритм Кана (топологическая сортировка)** — перед каждой итерацией симуляции риски упорядочиваются по причинно-следственным зависимостям из Байесовской сети. Алгоритм Кана строит линейный порядок, в котором каждый риск идёт после всех своих родителей в DAG. Это гарантирует корректный последовательный розыгрыш: вероятность реализации риска (через CPT) зависит от того, реализовались ли его родители, поэтому родители должны быть оценены раньше детей. Без топологической сортировки возникли бы циклические зависимости и некорректные вероятностные расчёты.

## LLM-интеграция

### Поиск связей (шаг 2) и привязка рисков (шаг 4)
- **API:** GigaCode (`gigacode.sberbank.ru`)
- **Модель:** настраивается в `main.py`
- **Consensus-режим:** N независимых вызовов, отбор связей по модальным значениям
- **Валидация:** фильтрация дублей, самосвязей, циклов, невалидных ID

### Семантические веса (шаг 6)
- **Промпт:** `6_semantic_weights_prompt.txt`
- **Механизм:** LLM оценивает смысловую связь между парами рисков по шкале 0–1
- **Consensus-режим:** N batch-запросов, усреднение весов и reasons по раундам
- **Формула:** `final = min(1.0, semantic × (1 + structural(d)))`

### Итоговый отчёт (шаг 10)
- **Промпт:** `10_llm_report_prompt.txt`
- **Механизм:** собирается контекст из результатов симуляции, Байесовской сети, КСГ и карты рисков → LLM формирует аналитический отчёт с рекомендациями

## Автоматическое кэширование LLM

Все вызовы LLM (шаги 2, 4, 6, 10) кэшируются в `cache/llm_cache/` по SHA256-хешу от:
- Входных данных
- Текста промпта
- Конфига `PIPELINE_CONFIG`

**Формат имён:** `stepN_{subtype}_{hash}.json`

| Шаг | Файл кэша |
|-----|-----------|
| 2 | `step2_consensus_{hash}.json` |
| 4 | `step4_consensus_{hash}.json` |
| 6 | `step6_{hash}.json`, `step6_consensus_{hash}.json` |
| 10 | `step10_{hash}.json` |

**Преимущества:**
- **Детерминизм** — одинаковые входные данные = одинаковые результаты
- **Скорость** — повторный запуск не требует вызова LLM
- **Автоинвалидация** — при изменении данных или промпта кэш обновляется
